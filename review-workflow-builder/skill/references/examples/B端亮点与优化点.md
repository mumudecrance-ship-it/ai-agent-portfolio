# 复盘 · B端亮点/优化点

## 业务问题
运营从评价里挖新亮点/新问题效率极低（月度识别比 0.1/0.2 量级）：词云只见高频、真亮点藏在场景化隐喻里、阴阳怪气差评混在好评里。目标自动化识别，运营只做审核。

## 依赖能力
评价查询服务（已过恶意过滤的评价，主数据口径）、词云服务（TOP10 正向高频词作排除项）、商品信息中心（参数）、推荐侧亮点效果数据（入参即可，不需RAG）、评价RAG（句子分片+rerank>0.7）、亮点沉淀库。

## 节点结构（平台节点口径，12 节点）
逐条评价迭代 → 沉淀库比对(code：仅含已识别亮点则跳过) → 判断新亮点prompt(llm，词云TOP10/已有标签/新发现亮点作入参) → 找相同亮点评论(knowledge_retrieval+rerank，TOP20带引用) → 语句打标(code，二次执行剔除) → 生成亮点标签prompt(llm，商品参数+同类优秀亮点入参；可再拆为找参数+生成两节点) → 运营人审(end转审) → 旁路：沉淀未审核亮点入库 / 低效标签识别工作流（已有标签近一月无人提及→运营判断下线）

## 方法论要点
- **开销双机制是本条精髓**：沉淀跳过（实线/虚线）+ 语句打标剔除——每晚全量跑的前提
- 逐条执行不追求批量：并行总开销一致，且批量会破坏沉淀跳过
- 与推荐侧数据互换：亮点关联原始评论与账号给推荐，推荐回给亮点效果库（⑤解耦+生态）
- 问题识别线：必须跑正向评价识别阴阳怪气（embedding 辅助）；老问题也记录，新问题按已知类型定严重度
